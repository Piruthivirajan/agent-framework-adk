### 2026-10-12: hardening 7, egress rule for the cloud metadata address

### 2026-10-12: hardening 5, failures told apart: a dead database is not "not found", explicit Gemini timeout and retry
- **Bigger than the finding.** Writing the test for "database down" showed ADK catches a tool's exception (`FunctionTool` logs "Exception occurred while calling function tool") and hands the model an error text. The model then does what the prompt tells it after a bad search: answers NOT_FOUND. So a MongoDB outage, an embedding 429 or a reranker failure reached the user as the honest-looking "Not found in the reference documents." Fixed in code, not in the prompt: `SearchDocumentsTool` catches the failure, records it in `RetrievalLedger.recordFailure`, and returns `SEARCH_FAILED` to the model (do not search again); `ChatService.decide` throws `ChatFailedException` (cause kept) when a search failed and nothing was retrieved. If an earlier search in the same turn did retrieve, the turn goes on with that.
- `ErrorMapping.of`: any `MongoException`/`DataAccessException` anywhere in the cause chain (depth-bounded, cycle-safe) maps to `DATABASE_UNAVAILABLE` / 503 *before* the model mapping, so "Timed out after 30000 ms" from the Mongo driver is no longer called a model timeout.
- Gemini limits: `LimitedLlm` wraps the one model `GeminiModelFactory` creates and puts per-request `HttpOptions` on every call: timeout 60 s (OkHttp call timeout, retries included) and `HttpRetryOptions` attempts = retries+1 = 2, initial delay 1 s, x2, max 8 s, jitter, status codes 429 and 503 only. Config `agentfw.llm.request-timeout-seconds`, `agentfw.llm.retries` (0 to 5). Verified in the library bytecode before use (genai 1.75.0: `timeout` is milliseconds, `attempts` includes the first call, delays are seconds); note the genai client already retried 5 times by default on 408/429/5xx, which this replaces for chat.
- Embeddings: the client gets the same 60 s timeout and no client-level retry (the existing backoff loop is the only one, so attempts no longer multiply); a *query* embedding now retries once, ingestion keeps its configured retries.
- Tests: `LimitedLlmTest` (7) runs the real ADK `Gemini` against a local HTTP server: 429 then 200 succeeds with 2 requests; 503 likewise; a persistent 429 stops after exactly 2; retries 0 = 1 request; 400 and 500 are not retried; a 6 s response with a 1 s timeout gives up in under 5 s. `ErrorMappingTest` (7): mapping unit tests plus two real ADK turns (database exception, rate-limited embedding) that must end as `DATABASE_UNAVAILABLE` / `MODEL_RATE_LIMITED`, never as a NOT_FOUND answer.
- Not changed: the MongoDB driver's own timeouts (server selection 30 s default) still apply, so an outage costs the user up to 30 s before the message.

### 2026-10-12: hardening 4, every configured MCP credential redacted by exact value
- Finding: only Google-key-shaped strings were masked. A server that echoed its `Authorization` header (or a model that repeated it) would have shown the token in the trace, the answer, an error and, worse, to the language model.
- `Secrets` now also holds *tracked values*: `McpRegistry` registers, on every add/update/remove/restore, `McpServerConfig.secretValues()` = every header value exactly as configured, the token part of a `Scheme token` value (a server may echo just the token), and the URL's query string, query values and user info. `Secrets.mask` replaces them (longest first) in addition to the Google-key pattern; values under 4 characters are not registered (they would damage ordinary text). Owners are held weakly.
- Applied where the credentials could travel: `RecordingMcpTool` masks the result *before it is recorded and before it is returned to the model* (`Secrets.maskDeep` over the nested map), the recorded arguments, and error text; `ChatService.mcpResult` masks the final sentence (the model may repeat an echoed value); `McpRegistry` masks failure messages in views and its debug log; the existing `Secrets.mask` call sites (`ErrorMapping.clean`, `GlobalExceptionHandler`, `ChatService` logs) get the tracked values for free. The test-connection button tracks the unsaved config's values while it runs.
- Tests: `SecretsTest` (5), `McpAnswerPathTest.aCredentialTheServerEchoesBackNeverReachesTheTraceTheModelOrTheAnswer` (the demo server echoes an unknown order id, which here is the token: the trace, the answer and every tool result the model was shown are clean).

- Not covered: ADK's own debug logging of requests (off at the default log level), and values that a server transforms (base64, URL-encoding, truncation) before echoing.

### 2026-10-12: hardening 3, MCP servers persisted in MongoDB, encrypted
- Finding: the registry was memory-only, so a redeploy on the VM emptied the MCP settings.
- `McpConfigStore` (interface) with two implementations chosen in `McpStoreConfiguration`: `MongoMcpConfigStore` (collection `mcp_servers`) when `AGENTFW_MCP_SECRET_KEY` is a valid key, otherwise `MemoryOnlyMcpConfigStore`, which carries the sentence the settings page shows ("kept in memory only ... because no encryption key is configured", or "key is not valid"). Credentials are never written unencrypted: an invalid key does not fall back to plain text.
- `McpSecretCipher`: AES-GCM, random 96-bit IV per value, key = base64 of 16/24/32 random bytes (not a passphrase: no KDF/salt needed). The server id and field name are authenticated (AAD), so a value copied to another field or server fails. Encrypted: every header value and the URL (a token can sit in its query string). Clear: id, name, transport, enabled, header names (the page shows them anyway).
- `McpRegistry`: `store.save/delete` happens before the in-memory change (database down: nothing changed, the user gets the DATABASE_UNAVAILABLE message); on `ApplicationReadyEvent` the saved servers are loaded and connected in a background thread (status `CONNECTING`, then `CONNECTED`/`ERROR`), `McpConfigChanged` is published when done; a database that is down at start is retried on the next list call; servers this key cannot decrypt are counted (`storage().unreadable`) and left untouched in the database. New endpoint `GET /api/mcp/storage`; the page shows the note and the unreadable count and polls while a server is connecting.
- `scripts/deploy.sh` generates the key once into `.env`; `docker-compose.prod.yml` passes it; `.env.example` and docs updated. `restore-db.sh` restores only `chunks`, so saved servers survive `--restore-db`.

### 2026-10-11: Day 5 step 7, "add to knowledge base" (`POST /api/kb/documents`)

### 2026-10-11: Day 5 step 3, `MapReduceSummarizer`
- **Single pass** up to `agentfw.summary.single-pass-max-chars` (30,000, starting value): one call, the user's instruction applied directly. **Map-reduce** above it: split at paragraph boundaries (then line breaks, sentence ends, spaces, hard cut; no text lost, tested) into segments of about 15,000 characters; each segment gets a *neutral* "dense partial summary" prompt (the instruction is applied only at the end, so "three bullet points" does not produce three per segment); partials are combined in order by one reduce call; partials too long for one call (`reduce-max-chars`) are reduced in groups, repeatedly (at most 6 rounds, and each round must shrink).
- **Parallelism** is bounded (4) to stay inside rate limits; each model call is retried twice with backoff; **if a call still fails the whole summary fails** with a message naming the part ("Part 3 of 24 could not be summarized by the model after 3 attempts: ..."), nothing is silently dropped. A text needing more than `max-segments` (120) map calls is refused before any call.
- **Data, not instructions:** the text is passed between `<document>` / `<parts>` tags and the system instruction says never to follow instructions inside it; the summarizer has no tools, so a hostile file can at most distort its own summary.
- **Progress callback** (`summarizing parts i/n`, `condensing`, `combining`) is there for the SSE events of step 6.
- Built on the `TextGenerator` seam, tested with a fake model (13 tests): single pass, neutral map prompts, order, call counts, the parallel bound, grouped reduce, retry then success, failure naming the part, segment limit, progress, splitting.
- Not measured yet: real latency and quality on large files (step 9).
- Verified: BUILD SUCCESS, 233 tests.

### 2026-10-11: Day 4 step 3, grounding verifier
- `GroundingVerifier.verify(modelOutput, requestId)` is plain code after the model. The answer is shown only if **every** claim passes; otherwise the whole answer becomes "Not found in the reference documents." A claim passes when: its `ref` was returned by retrieval **in this request** (ledger lookup); its quote has at least 25 characters and 4 words (and at most 400); the quote occurs in that chunk's text after NFKC and whitespace normalisation, case and punctuation exact; every number in the claim's `text` also occurs in **its quote** (the chunk containing the number is not enough), with formats normalised (`1,000` = `1000`, `14.0` = `14`, `09` = `9`).
- Rendering is by code: `claim text [file, p. N]` per claim, file and page from the ledger (the model cannot mis-cite). The quotes go in a separate `sources` list (`ref`, `file`, `page`, `quote`, de-duplicated), not in the answer text. Any prose or extra JSON fields outside the claims are never shown.
- Fail closed: no JSON, wrong status, no claims, more than 6 claims, missing field, unknown ref, a ref from another request. `modelSaidNotFound` separates "the model itself said NOT_FOUND" from "the verifier rejected it", for the end-to-end report. All problems are listed, not only the first.
- Limit, stated plainly: this guarantees provenance (the shown sentences have quotes that exist in retrieved documents), not entailment. The numeric rule closes the most dangerous gap (a real quote next to a figure from the model's memory). Word numbers ("fourteen") and unit or entity changes are not checked.
- Tests (pure code): accepted claim and rendering; whitespace and no-break-space and line-break normalisation; NFKC ligature; number formats; de-duplicated sources; fences and prose around the JSON tolerated but never rendered; extra fields ignored; fabricated quote rejects the whole answer including good claims; real quote on the wrong chunk; unknown ref and cross-request ref; case sensitivity; short and long quotes; numeric support (a figure only in the chunk, not the quote, is rejected; 1,000 is not 1,000,000); eleven contract violations all fail closed.
- Verified: BUILD SUCCESS, 163 tests.

### 2026-10-10: Day 2 step 3, chunking
- `Chunker` slides a window of 650 estimated tokens (chars / 4) over each page with 15% overlap; chunks never cross a page, so each has one citable page number. Each chunk ends at the best boundary in the last 25% of the window: paragraph break, then sentence end, then space; with no boundary at all it cuts hard (and still terminates).
